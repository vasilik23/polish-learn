# Проектирование отправки результатов и offline-синхронизации

Документ фиксирует следующий контракт для отдельного мобильного/PWA-клиента.
Это проектирование, а не уже опубликованный endpoint или обещание offline-режима.

## Граница контракта

Планируемый `POST /api/v1/me/lesson-results/` принимает Supabase bearer token и
результат только текущего пользователя. `user_id` не передаётся в теле: Django
получает его из проверенной сессии, а запись в Supabase выполняется с тем же
access token через owner-scoped RLS.

Минимальный запрос содержит:

- `event_id` — UUID, созданный клиентом один раз до первой попытки отправки;
- `lesson_id`, `plan_date`, `completed_at`;
- `cards_total`, `cards_known`;
- `contract_version` и необязательный `client_instance_id` для диагностики.

Сервер проверяет существование активного урока, диапазоны чисел, допустимую
дату и размер запроса. Токены, email и профиль в payload запрещены.

## Идемпотентность

Уникальная граница — `(user_id, event_id)`. Сервер хранит hash нормализованного
payload вместе с immutable событием.

- первая валидная попытка создаёт событие и возвращает `201`;
- повтор того же `event_id` с тем же hash возвращает прежний результат и `200`;
- тот же `event_id` с другим payload возвращает `409 idempotency_conflict`;
- сетевой timeout после записи безопасно повторяется с тем же `event_id`.

Текущая `lesson_completions` становится серверной проекцией событий. Повторная
синхронизация не уменьшает уже подтверждённый прогресс и не создаёт второй
completion за тот же урок и дату.

## Offline-очередь и конфликты

Клиент может хранить только минимальный payload и статус события в IndexedDB
или защищённом хранилище приложения. Access/refresh token не входит в очередь.
Отправка начинается после восстановления сети и действующей сессии; при `401`
очередь остаётся локально и интерфейс просит войти снова.

События отправляются по времени создания, но сервер не доверяет порядку
доставки. Успешные элементы удаляются только после ответа с подтверждённым
`event_id`. Ошибки `409` и постоянные `4xx` требуют видимого решения
пользователя; временные `5xx` повторяются с ограниченным exponential backoff.
Очередь показывает количество ожидающих результатов и позволяет отказаться от
неотправленных данных.

## Перед реализацией

1. Добавить совместимую event-таблицу парными Django/Supabase миграциями.
2. Включить RLS и grants только для `authenticated`; `SELECT` и `INSERT`
   ограничить `(select auth.uid()) = user_id`, не принимать владельца из body.
3. Закрепить duplicate/retry/conflict, BOLA и размер payload тестами.
4. Проверить security/performance advisors и production smoke до включения
   offline-очереди.
5. Оставить существующий online-путь рабочим до отдельного управляемого rollout.
